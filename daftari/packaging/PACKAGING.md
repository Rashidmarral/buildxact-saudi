# Packaging Daftari for CodeCanyon

Internal, operator-facing notes for building a release zip. Not part of the
customer-facing documentation set (see `docs/codecanyon/DOCUMENTATION.md` for
that).

## Package structure

Two separate concerns, kept apart:

```
daftari-vX.Y.Z-full.zip        <- what most buyers install
daftari-vX.Y.Z-source.zip      <- source-only alternative
Documentation.pdf / .html      <- built separately from docs/codecanyon/DOCUMENTATION.md
```

Envato's own item requirements ask that installable code and documentation
ship as clearly separate downloads, not interleaved — CodeCanyon's upload
flow accepts multiple files per item precisely for this reason. Don't zip
the documentation inside the same archive as the source.

**Demo assets**: none are needed as a separate download. The item's live
preview should point at a hosted demo running `demo:install` (Module 23),
not a bundled data file — sample data is generated by that command, not
shipped as static fixtures.

### `-full.zip` (recommended default)

Application source **plus** a `vendor/` built via `composer install
--no-dev` and compiled front-end assets in `public/build/`. This is what the
majority of CodeCanyon PHP/Laravel buyers need: most run on shared hosting
with no SSH or Composer access, so they unzip, point a domain at `public/`,
and use the `/install` wizard (Module 24) directly.

### `-source.zip` (for technical buyers / your own deploys)

No `vendor/`, no `node_modules/`, no compiled assets. Whoever installs this
runs `composer install` and `npm install && npm run build` themselves. Keep
this available since some buyers specifically want to audit or customize
the dependency tree before installing.

## What never goes in either zip

Enforced by `build-package.sh`'s exclude list — this is the authoritative
"do not include" checklist, cross-referenced against Module 25's audit:

| Excluded | Why |
|---|---|
| `.git/`, `.github/` | Full commit history — including anything ever committed and later "removed" — must never leave this repo. `git log`/`git show` still reveal it. |
| `.env`, `.env.backup`, `.env.production` | Real database/mail/payment/ZATCA credentials for *some* deployment. `.env.example` ships instead. |
| `.env.testing`, `phpunit.xml`, `tests/` | Test-only configuration and the test suite itself — not part of the product. |
| `node_modules/` | Rebuilt by the buyer (`-source.zip`) or already compiled into `public/build/` (`-full.zip`) — never needed at runtime either way. |
| `vendor/` (source zip only) | Rebuilt via `composer install`; the full zip ships a `--no-dev` build instead so `laravel/pail`, `laravel/sail`, `phpunit/phpunit`, etc. never reach a buyer's server. |
| `database/*.sqlite` | The local dev/demo database file — may contain whatever data a developer's machine last seeded. |
| `.phpunit.result.cache`, `.phpunit.cache/` | Local test run artifacts. |
| `storage/logs/*.log` | Development log output. Empty `storage/logs/.gitignore` placeholder ships so the directory exists. |
| `storage/framework/{cache,sessions,views,testing}/*` | Runtime-generated cache files. |
| `storage/app/public/*` | Any files uploaded to a *developer's* local instance (logos, attachments) — a buyer starts with an empty disk. |
| `docs/module-*-testing.md` | Internal engineering test notes (e.g. `module-05-payment-testing.md`), not customer documentation. |
| `.idea/`, `.vscode/`, `.fleet/`, `.nova/`, `.zed/`, `.DS_Store` | Editor/OS artifacts. |

**`database/seeders/RealCompanySeeder.php`** deserves its own line: it is
**not** excluded by the build script (it's ordinary application source), but
as of Module 25 it is no longer called by `DatabaseSeeder`, so a buyer's
`migrate --seed` never runs it. It still contains one specific operator's
real company registration numbers, bank IBAN, and a working login password
in plaintext. Before this repository is used as the basis for a public
CodeCanyon listing, delete this file outright (or move it out of the repo
entirely) rather than relying on it staying uncalled — see the Module 25
final report's Security Issues section for why, and rotate both passwords
shown in it if either account is still in real use anywhere.

## Building

```bash
packaging/build-package.sh 1.0.0
```

Everything happens in `packaging/build/` (a throwaway copy) — your working
checkout's own `vendor/`, `.env`, and git history are never touched. Output
lands in `packaging/dist/`.

## Before every upload — manual checklist

1. Run the audit sweep again for anything committed since the last release
   (see the Module 25 report's "Security/Secrets audit" methodology —
   re-run those `git grep` patterns).
2. Confirm `composer.json`'s `license` field and an actual `LICENSE`/EULA
   file reflect the real terms you're selling under — `proprietary` in
   `composer.json` is a marker, not a legal document; CodeCanyon requires
   you to state your own licensing terms at upload time.
3. Unzip the `-full.zip` output somewhere clean and run through `/install`
   end to end against a real, empty MySQL database (not SQLite) before
   uploading — this repo's own automated tests run against SQLite; a
   MySQL-only bug would not be caught by them (see the Module 25 report's
   Compatibility Issues section).
4. Bump the version shown in `config/daftari.php`'s `version` key so it
   matches the zip's filename.
